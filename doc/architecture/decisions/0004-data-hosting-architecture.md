# 4. Data Hosting and Access Architecture for the Swedish Pathogens Portal

**Date:** 2026-01-13

## Status

Draft.

## Context

The Swedish Pathogens Portal (SPP) provides a national entry point for discovering research outputs related to infectious disease and pandemic preparedness generated by Swedish research organisations.

As the portal evolves into Swedish Pathogens Portal 2.0 (SPP 2.0), there is a need to support **structured, user-friendly access to heterogeneous research datasets** (e.g. metabolomics, genomics, proteomics) while preserving clear provenance and alignment with established international repositories.

Most datasets relevant to the portal are deposited and curated in **authoritative external repositories** (e.g. EMBL-EBI resources such as ENA or MetaboLights). The portal should therefore not replicate large primary datasets, but instead provide:

- Harmonised, searchable metadata across data types and units  
- Clear indication of repository-of-record and provenance  
- Direct download links with minimal user friction  
- Consistent access patterns across the portal and topic pages  

This ADR outlines the proposed architecture for the **flow of data between producing units, storage solutions, and the portal’s data pages**, starting with metabolomics data and designed to scale to additional data types.

## Decision

We will implement a **metadata aggregation architecture** for hosting and accessing data in Swedish Pathogens Portal 2.0.

The portal will maintain a **central metadata store** that aggregates and harmonises dataset-level metadata from multiple sources, while primary data files remain hosted in external authoritative repositories.

The portal’s data pages will query this central metadata store and provide users with:

- Search and faceted filtering across datasets  
- Topic- and pathogen-driven discovery  
- Direct links to download data from the repository-of-record  
- Lightweight metadata exports (e.g. TSV/JSON)  

## High-level Architecture

```
Research units / platforms
        ↓
Authoritative repositories
(e.g. ENA, MetaboLights, others)
        ↓
Metadata ingestion pipelines
        ↓
Central metadata store (SPP 2.0)
        ↓
Portal data access layer
        ↓
Portal UI (data pages & topic pages)
```

## Storage Solution

### Selected approach

A **portal-managed metadata store** within Swedish Pathogens Portal 2.0.

### Scope of stored data

The metadata store will include:

- Dataset identifiers (internal and external accessions)
- Data type (e.g. metabolomics)
- Pathogen(s)
- Topic(s)
- Repository-of-record
- Key experimental metadata (e.g. sample matrix, platform, year)
- Direct download URLs
- Provenance and timestamps

Primary data files will **not** be stored in the portal database.

## Data Ingestion

### Data sources

- International repositories (e.g. EMBL-EBI services)
- Unit-provided metadata exports (CSV/JSON)
- Future national or international APIs

### Ingestion mechanisms

- Scheduled metadata harvesting via APIs
- Batch imports for initial or legacy datasets
- Manual curation for early-stage or pilot data types

## Data Access in the Portal

### Portal data pages

- Data-type–specific pages (e.g. `/data/metabolomics/`)
- Faceted filtering and free-text search
- Repository badges and direct download links

Users should be able to reach downloadable data in **no more than two clicks** from the portal homepage.

### Topic page integration

- Topic pages surface “Available data” sections
- Same metadata store used across all portal views

## Out of Scope

- Hosting primary data files
- User authentication and RBAC
- Sensitive or controlled-access data handling
- Detailed per–data type schema definitions

## Alternatives Considered

### Direct proxying of repository APIs

Rejected due to tight coupling and inconsistent UX.

### Full data replication in the portal

Rejected due to storage cost and conflict with repository-of-record principles.

## Consequences

### Positive Outcomes

- Improved discoverability
- Consistent UX across data types
- Scalable, FAIR-aligned architecture

### Risks & Mitigation

- Ingestion pipeline maintenance → automate and monitor
- Metadata freshness → scheduled updates
